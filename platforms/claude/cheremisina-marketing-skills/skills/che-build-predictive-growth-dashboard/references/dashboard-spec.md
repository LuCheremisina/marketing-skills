# Спецификация интерактивного дашборда

## Содержание

1. Управленческая логика
2. Обязательные секции
3. Визуальные правила
4. Фильтры
5. Артефакт и публикация
6. QA

## 1. Управленческая логика

Построить чтение сверху вниз:

`ожидаемый результат → статистический диапазон → управленческие сценарии → причины → бизнес-ценность → блокеры → действия → качество модели`.

Каждый крупный график отвечает на один вопрос. Не создавать график только потому, что данные доступны.

На первом экране собственник должен понять:

1. Сколько ожидается на 7 и 30 дней.
2. Насколько прогноз надёжен.
3. Что изменит траекторию.
4. Какие три действия приоритетны.

## 2. Обязательные секции

### 1. Executive layer

Показать:

- базовый прогноз P50 на 7 и 30 дней;
- P10/P90 отдельно от пессимистичного/оптимистичного сценария;
- изменение к сопоставимому факту;
- WAPE 7 и WAPE 30;
- выигрыш модели относительно baseline;
- confidence базы и сценариев;
- дату актуальности и статус снимка;
- максимум три приоритетных действия.

Не сворачивать разные типы диапазона в одну пару «от–до».

### 2. Факт, статистический диапазон и сценарии

Использовать временной график:

- фактический скорректированный ряд;
- базовая линия P50;
- полоса P10–P90;
- пессимистичная и оптимистичная линии;
- аннотации подтверждённых событий и change points.

Дать переключатель или ясную легенду, чтобы статистическая неопределённость не выглядела как результат действий.

Не смешивать на одной шкале трафик, CTR, позиции и деньги.

### 3. Качество модели

Показать:

- кандидатов и выбранную модель;
- baseline;
- WAPE, MAE, MASE и bias по 7/30;
- разброс ошибки по backtest-folds;
- число fold-окон;
- фактическое покрытие P10/P90;
- обучающее окно и последнюю смену режима;
- fingerprint или короткий идентификатор воспроизводимого входа.

Предпочесть компактную таблицу и небольшой график ошибок. Не превращать технический блок в главный экран.

### 4. Поисковая и бизнес-воронка

Показать раздельно:

`Wordstat спрос → Вебмастер показы → клики и CTR → Метрика визиты → CTA → квалифицированные лиды → сделки → валовая прибыль`.

Для каждого слоя указать источник и статус. Если нижний слой не подключён, показать readiness-gap, а не ноль.

Рядом с объёмом трафика показать бизнес-ценность:

- коммерческие визиты;
- переходы к услугам и продуктам;
- CTA-конверсии;
- квалифицированные лиды;
- финансовый слой только при сверенной CRM.

### 5. Структура роста

Показать согласованные разрезы, которые меняют решение:

- коммерческий, информационный и брендовый интент;
- услуги, продукты, статьи и хабы;
- ключевые тематические кластеры;
- каналы и AI-referral при надёжной разметке;
- устройства или регионы, если эффект существенен.

Для полного разреза показывать контроль:

`сумма сегментов = общий прогноз`.

Для частичного — coverage share и явное ограничение.

### 6. Драйверы, риски и события

Показать:

- изменение спроса;
- показы, клики и CTR;
- ведущие страницы и концентрацию топ-1/5/10;
- технические и индексные сигналы;
- будущие публикации, рассылки, выступления, кампании и релизы;
- 3–7 драйверов;
- 3–7 блокеров с доказательством, вероятностью и дневной потерей.

Отделять наблюдаемый сигнал от предполагаемой причины.

### 7. Радар спроса и видимости

Для кластеров показывать:

- направление спроса;
- частотность и сезонность;
- видимость сайта;
- интент и бизнес-ценность;
- текущий URL или gap;
- продукт и CTA;
- действие: `protect`, `improve_ctr`, `update`, `create`, `watch`, `review`;
- уверенность.

Не называть тему приоритетной только по высокой частотности. Коммерческий кластер меньшего объёма может быть важнее массового информационного спроса.

### 8. План на 7 и 30 дней

Таблица действий содержит:

`приоритет → действие → рычаг → baseline → target → старт → лаг → вероятность → доказательность → эффект 7/30 → стоимость/ресурс → зависимость → done_when`.

Показать:

- дневную кривую эффекта;
- вклад в optimistic gap;
- `interaction_group` и overlap discount;
- доступный потолок эффекта;
- действия по устранению блокеров данных.

Не показывать точечный эффект без диапазона.

### 9. Обучение на предыдущих прогнозах

Для обновляемой панели показать:

- прогноз vs факт по завершённым 7/30-дневным окнам;
- изменение WAPE и bias;
- выполненные/невыполненные действия;
- фактический эффект и метод идентификации;
- обновлённое доверие к рычагам.

Для первого запуска показать «контур обучения инициализирован», а не пустой график.

### 10. Качество данных и ограничения

Показать:

- статус, покрытие и свежесть источников;
- исходные корректировки и исключённые периоды;
- отсутствующую детализацию;
- ограничения интерпретации рядом с ограниченным выводом;
- дату следующего обновления, если она определена.

## 3. Визуальные правила

- Использовать нейтральные описательные заголовки.
- Выносить вывод в подзаголовок только при доказательстве данными.
- Не использовать больше hero-карточек, чем нужно для решения.
- Использовать line chart для динамики, ribbon/area для P10–P90, bar chart для сравнения, scatter/quadrant для кластеров и таблицу для действий.
- Показывать сценарии линиями, статистический интервал — полосой; не кодировать оба слоя одинаково.
- Показывать легенду для нескольких сценариев или групп.
- Не использовать цвет как единственный носитель смысла.
- Соблюдать единицы, шкалы и даты во всех блоках.
- Выделять риск и действие разными визуальными ролями.
- Сохранять бренд-стиль проекта, но не жертвовать читаемостью.

## 4. Фильтры

Добавлять только фильтры, которые меняют решение:

- горизонт 7/30;
- сценарий и статистический диапазон;
- источник или канал;
- тип интента;
- раздел сайта;
- поисковый кластер;
- продукт/услуга;
- критичность блокера;
- статус и доказательность действия.

Не перегружать верхнюю часть. По умолчанию панель должна быть полезна без взаимодействия.

## 5. Артефакт и публикация

Создать canonical Data Analytics manifest и bounded snapshot:

- `snapshot.datasets` — объект, где каждый dataset содержит массив строк;
- не более 50 datasets;
- не более 2 000 строк на dataset;
- не более 3 MB payload;
- не более 200 000 inline source characters.

Рекомендуемые datasets:

- `actual_series`;
- `daily_forecast`;
- `scenario_totals`;
- `uncertainty_totals`;
- `backtest_summary`;
- `backtest_folds`;
- `funnel`;
- `hierarchy`;
- `drivers`;
- `blockers`;
- `actions`;
- `learning_evaluations`;
- `source_quality`.

Указать источники, определения метрик, даты и существенные исключения. Использовать `accessIssues` только при частичном или заблокированном результате, когда отсутствующие данные действительно ограничивают панель.

Перед публикацией вызвать `validate_artifact` с полным manifest и snapshot. Исправить ошибки до передачи.

В Work Mode:

1. Не использовать `render_artifact`, `render_chart` или `render_table` для финальной передачи.
2. Экспортировать валидированный пакет через Data Analytics.
3. Переиспользовать существующий Sites `project_id`, если панель уже существует.
4. Сохранить стабильные component IDs и presentation overrides.
5. Создать checkpoint, сохранить version и развернуть её.
6. Проверить терминальный статус deployment.

Для новой панели без запроса на широкий доступ использовать приватный режим. Для обновления не менять политику доступа без прямой просьбы.

Сообщать, что опубликованные данные являются снимком, если live-refresh не реализован.

## 6. QA

Перед передачей проверить:

- панель открывается по итоговому URL;
- новая версия опубликована по прежнему адресу при обновлении;
- фильтры работают;
- карточки, графики и таблицы согласуются;
- дневные сценарии сходятся с 7- и 30-дневными итогами;
- P10/P50/P90 не названы сценариями;
- WAPE 7 и 30 показаны раздельно;
- видимые даты и часовой пояс корректны;
- источник и свежесть каждой ключевой метрики доступны читателю;
- query-level выводы не сделаны из агрегатных данных;
- optimistic gap покрыт действиями по датам;
- pessimistic gap покрыт рисками по датам;
- взаимодействия действий не посчитаны дважды;
- полные сегментные разрезы сходятся с общим прогнозом;
- readiness-gap не показан нулём;
- коммерческая ценность не подменена объёмом трафика;
- блокеры не спрятаны в сноску;
- пользователь видит не более трёх первоочередных действий в executive layer;
- для обновления показан факт предыдущего прогноза либо объяснено отсутствие завершённого горизонта.
