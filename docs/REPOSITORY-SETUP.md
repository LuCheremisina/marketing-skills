## Community

Enable Discussions. Use **Q&A** for installation questions, **Ideas** for skill requests and **Show and tell** for examples. Category forms ask for the client and workflow, expected outcome and a synthetic or public example. Contributions may improve documentation without changing skill instructions. Keep issue reports for reproducible repository defects.

## Public presentation and maintenance

Use `assets/social-preview.png` as the GitHub social preview. The SVG is the editable source; a committed image alone does not prove the remote preview is configured. Set the homepage to the public methodology site. Protect the default branch and require successful checks for update PRs.

Publish accepted release archives and manifests as immutable versions. Documentation changes do not require rebuilding an existing release. Test repository and download URLs without signed-in access. Watch releases for updates.

## Measure discovery

GitHub's Traffic view retains a rolling 14-day window for views, visitors, clones, referrers and popular paths. Snapshot it regularly in a private report. Release asset counters measure downloads, including tests and repeat downloads; they do not prove unique installations. Compare changes against a dated baseline and label self-test traffic separately. The proposed 100 stars and 300–500 downloads are campaign targets, not a forecast or ranking threshold.

Record directory submissions and their actual acceptance separately from prepared drafts. Follow each directory's contribution requirements, including minimum stars or usage evidence. Search by exact repository name and relevant use-case queries after publication; retain dates and actual findings. Pending indexation is not proof of failure or an SEO guarantee. Business websites and skill methodology are outside this documentation task.
