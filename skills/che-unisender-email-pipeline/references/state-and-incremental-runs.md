## 1. Назначение

Постоянное состояние переносит доказательства между запусками. Оно не заменяет источники истины, а хранит полученные из них нормализованные наблюдения, охват, пробелы, редакционные решения и идентификаторы черновиков.

Не полагаться на память модели или историю чата: новый запуск может не видеть предыдущий разговор.

## 2. Где хранить

Каноническое имя: `email-pipeline-state.json`.

Приоритет:

1. явно настроенное постоянное хранилище проекта;
2. библиотека файлов среды, если её сохранность и доступ проверены;
3. локальный файл проекта при подтверждённой сохранности между запусками.

Не зависеть от конкретной платформы; доступность хранилища проверить практически.

Не хранить живое состояние в папке Skill: Skill содержит методику и скрипты, а не меняющиеся данные проекта.

## 3. Контракт состояния

Синтетический пример минимальных верхнеуровневых полей:

```json
{
  "schema_version": 1,
  "project_key": "synthetic-email-project",
  "state_revision": 1,
  "updated_at": "2026-01-19T10:00:00+07:00",
  "coverage": {
    "baseline_through_sent_at": "2026-01-10T07:18:33+07:00",
    "latest_campaign_id": "synthetic-campaign-01",
    "baseline_snapshot_ids": ["synthetic_baseline_01"]
  },
  "baseline_snapshots": [],
  "campaign_observations": [],
  "link_snapshots": [],
  "web_analytics_snapshots": [],
  "crm_snapshots": [],
  "wordstat_observations": [],
  "content_registry": [],
  "recommendations": [],
  "experiments": [],
  "draft_registry": [],
  "run_history": []
}
```

`baseline_snapshots` сохраняет исторические агрегаты, если детальные строки старых кампаний недоступны. Не разворачивать агрегат обратно в вымышленные кампании. Новые кампании после cutoff добавлять отдельно и не дублировать в старом snapshot.

`campaign_observations` хранит срезы по ключу `campaign_id + observation_window + as_of`. Для текущего представления выбирать самый поздний `as_of` внутри одного окна; D+1/D+3 не заменяет D+7.

## 4. Жизненный цикл запуска

1. Найти и загрузить state.
2. Проверить schema, project key, уникальность ключей и ISO-даты.
3. Построить refresh plan.
4. Получить только новые кампании и перечисленные пробелы.
5. Сформировать отдельный `run_delta.json`; не менять базовый файл во время сбора.
6. Объединить state + delta в новый файл.
7. Валидировать новый файл и пересчитать производные показатели.
8. Сохранить новую версию atomically; старую версию не удалять.

## 5. Правила объединения

- Списки объединять по стабильным ключам, не конкатенацией.
- `campaign_observations`: `campaign_id|observation_window|as_of`.
- `link_snapshots`, `web_analytics_snapshots`, `crm_snapshots`, `baseline_snapshots`: `snapshot_id`.
- `wordstat_observations`: `phrase|region|observed_at`.
- `content_registry`: canonical URL без UTM.
- `recommendations`: `recommendation_id`.
- `experiments`: `experiment_id`.
- `draft_registry`: `draft_key`; подтверждённый `message_id` нельзя заменить пустым или неизвестным.
- `run_history`: `run_id`.
- `null` не должен затирать известное значение. Новое непустое значение может обогатить старую запись.
- При конфликте двух известных значений сохранять более позднее наблюдение и provenance; не исправлять историю молча.

Производные rates не считать первичными данными. Пересчитывать их из totals после merge.

## 6. План дозагрузки

`plan` должен вернуть:

- `fetch_campaigns_after` — cutoff для новых кампаний;
- `mature_campaigns` — сохранённые D+1/D+3, уже достигшие D+7;
- `source_gaps` — кампании и источники со статусом `missing`/`partial`;
- `previous_experiment` — тест, результат которого нужно проверить первым;
- `duplicate_guard` — известные draft keys и message IDs.

Полный повторный сбор допустим только для восстановления повреждённого state, изменения методики или явной команды пользователя.

## 7. Версионирование и восстановление

Каждый успешный merge увеличивает `state_revision` на 1 и добавляет `run_history`. Постоянное хранилище должно сохранять версии файла.

Если state повреждён:

1. не перезаписывать его пустым объектом;
2. попробовать предыдущую версию;
3. сохранить новые данные как recovery delta;
4. пометить запуск `state=invalid`, `state_save=failed`;
5. не повторять внешние записи, опираясь только на отсутствие draft key в повреждённом файле.
