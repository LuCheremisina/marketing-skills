# SEO/GEO Auditor Pro

Проводить точечный экспертный анализ для ChatGPT и Codex. Масштаб результата
должен соответствовать запросу: проверка одного элемента не разворачивается в
полный аудит сайта.

## Маршрутизация

- Одна страница, title, meta description, Schema.org, контент-бриф, ссылка или
  отдельный технический вывод → этот skill.
- Независимая проверка списка подрядчика или доступности выбранных URL → этот
  skill.
- Полный crawl сайта с единым скорингом и отчётом → `seo-geo-auditor`.

## Выбрать режим

| Запрос | Результат |
|---|---|
| Один title/meta description | диагноз, версия правки, обоснование |
| Одна страница | интент, on-page, контент, CTA, GEO/AEO, приоритеты |
| Контент-бриф | цель, запросы, структура, FAQ, источники, Schema, CTA |
| Schema.org | применимый тип, обязательные поля, пример разметки |
| Индексируемость URL | HTTP, robots, meta/X-Robots, canonical, вывод |
| Кросс-проверка | подтверждено / ложное срабатывание / данных недостаточно |

## Процесс

1. Зафиксировать точный объект и критерий проверки.
2. Использовать доступный URL, сырой HTML, заголовки ответа, скриншот или
   выгрузку. Если решающего доказательства нет, запросить только его.
3. Отделить наблюдаемый факт от вывода и гипотезы.
4. Сопоставить проблему с поисковым интентом и бизнес-ролью страницы.
5. Дать минимально достаточное исправление и критерий повторной проверки.
6. Назначить приоритет: P1 — блокирует индексирование или ключевую конверсию;
   P2 — заметно влияет на релевантность и качество; P3 — улучшение.

## Частные проверки

### Одна страница

Проверять только применимое: назначение, интент, title/H1/meta, полноту ответа,
структуру, внутренние ссылки, CTA, E-E-A-T, FAQ, Schema.org и извлекаемость для
AI-ответов. Не заполнять шаблон полного аудита ради формы.

### Один title или meta description

Вернуть:

1. исходный элемент и фактическую длину;
2. один диагноз с привязкой к интенту и содержанию страницы;
3. одну основную версию правки, при необходимости — один альтернативный вариант;
4. длину новой версии и риски расхождения с содержанием страницы.

Не обещать CTR и позиции без данных эксперимента.

### Техническая и независимая проверка

Для индексируемости, SSR-дублей и сверки чужого аудита прочитать
`references/technical-cross-checks.md`. Не считать HTTP 200 доказательством
индексации, а данные Schema или hydration payload — дублем видимого контента.

## GEO/AEO

Оценивать ясность сущностей, прямые ответы, проверяемые источники, авторство,
сравнения, примеры, FAQ и структурированные данные. Рекомендовать блок только
когда он помогает пользователю и соответствует видимому контенту.

## Доказательность

- Не придумывать HTTP-статусы, директивы, мета-теги, позиции и трафик.
- Каждую техническую проблему связывать с URL и наблюдаемым фрагментом.
- При недоступности сайта работать по предоставленным данным и явно ограничить
  уверенность.
- Для меняющихся правил и рекомендаций проверять первичные источники.
- Не помечать рекомендацию P1 без доказанного блокирующего эффекта.

## Формат результата

Начать с вывода по объекту, затем показать доказательства, исправление и способ
перепроверки. Для нескольких находок использовать таблицу:

| Приоритет | Объект | Доказательство | Исправление | Проверка |
|---|---|---|---|---|

Перед выдачей применить `evals/shared.csv` и `evals/skill-specific.csv` по
`evals/judge_prompt.md`. Проверять критерии отдельно; неприменимое отмечать
`not_applicable`, общий балл не считать.

## Переносимость и запуск

Пути к ресурсам ниже относительны корню установленного навыка. Перед запуском
определи этот корень через механизм платформы; не предполагай текущую папку.
Относительные примеры CLI разрешай в абсолютный путь к скрипту, сохраняя рабочую
папку результата отдельно. Переменные и механизмы конкретной платформы задаются
её адаптером, не являются зависимостью универсальной методологии. Без Python, сети или коннектора запросить нормализованный вход или
вернуть ограниченный результат с явным статусом «не проверено».

Здесь capability обозначает возможность, а не гарантированное имя MCP-команды.
Вызовы в примерах — схема: сначала прочитать объявленные инструменты и сопоставить
аргументы. Не устанавливать зависимости, не создавать расписания, не публиковать
и не отправлять сообщения без применимого разрешения пользователя.
