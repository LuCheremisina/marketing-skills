# Wordstat Trend Radar

## Контракт зависимостей

- Обязательны публичные read-only methods MCP Panel
  `wordstat.regions.read`, `wordstat.top_requests.read` и
  `wordstat.dynamics.read`.
- Для сверки видимости опциональны
  `webmaster.queries.read`,
  `webmaster.query_history.read` и
  `webmaster.query_history.read`.
- Локальные Python-скрипты и SQLite используются только для вычислений и
  истории проекта; способ авторизации коннекторов определяет платформа.

Строить воспроизводимый радар спроса для одного проекта. Сначала зафиксировать границы исследования, затем собирать Wordstat. Не позволять новым формулировкам самопроизвольно менять ядро проекта.

## Обязательные артефакты

Хранить для проекта четыре файла и одну локальную историю:

1. `project-registry.json` — подтверждённые границы бизнеса.
2. `seed-manifest.json` — воспроизводимый список стартовых фраз.
3. `candidate-ledger.json` — все найденные запросы с решением и причиной.
4. `cluster-registry.json` — стабильные кластеры, алиасы, URL и история изменений.
5. `trend-history.sqlite` — наблюдения, снимки запусков и изменения сигналов; не хранить в нём ключи доступа.

Схемы и правила читать в:

- `references/project-registry.md` — обязательный реестр проекта;
- `references/clustering-policy.md` — отбор, объединение и стабильные ID;
- `references/data-contract.md` — контракты промежуточных и итоговых данных;
- `references/methodology.md` — расчёт трендов.

## 1. Создать или проверить реестр проекта

При первом запуске скопировать `assets/project-registry.template.json` в рабочую папку и заполнить:

- товары и услуги;
- категории продукта;
- аудитории;
- задачи клиентов;
- существующие URL;
- обязательные и запрещённые темы;
- уровни близости к продукту;
- пороги частотности;
- правила создания и объединения кластеров.

Получать данные из каталога, sitemap, меню, посадочных, статей и вводных пользователя. Не придумывать отсутствующий товар или услугу. Все предположения помечать `status: draft`.

Перед обращением к Wordstat выполнить:

```bash
python3 scripts/validate_registry.py project-registry.json --require-confirmed
```

Не запускать полный анализ, пока валидатор возвращает ошибки. Если данных не хватает, показать один консолидированный список пробелов. Разрешать только `discovery`-режим без стратегических рекомендаций.

Повторно подтверждать реестр только при изменении продукта, географии, аудитории, структуры сайта или правил отбора.

## 2. Сформировать стабильный seed-manifest

Создать стартовые запросы только из подтверждённых `seed_phrases` реестра:

```bash
python3 scripts/build_seed_manifest.py project-registry.json --output seed-manifest.json
```

Скрипт дедуплицирует фразы и сохраняет происхождение каждого seed: товар, категория, задача клиента или обязательная тема. Не генерировать новый набор seed заново при каждом запуске.

Новые seed-фразы сначала добавлять в реестр как `draft`, объяснять причину и только после подтверждения переводить в `active`.

## 3. Расширить спрос через Wordstat

Для каждого активного seed получить до установленного в реестре лимита:

```text
methodCode: wordstat.top_requests.read
params: {"phrase":"...","regions":[geo_id],"limit":200}
```

GeoID получать через:

```text
methodCode: wordstat.regions.read
params: {"search":"название региона"}
```

Каждый результат записывать в `candidate-ledger.json`, включая отклонённые запросы. Никогда не удалять фразу без причины.

## 4. Применить ворота отбора

Проверять кандидата в фиксированном порядке:

1. Запрещённая тема или значение → `reject`.
2. Неразрешённая неоднозначность → `reject` или `review`.
3. Нерелевантен продукту → `reject`.
4. Ниже минимальной частотности → `watch`, если тема обязательная или уже есть товар/URL; иначе `reject`.
5. Прямой или допустимый смежный спрос → `include`.
6. Исследовательская близость → `review`, не включать автоматически.

Использовать уровни из реестра, а не свободную оценку:

- `direct` — продукт решает запрос непосредственно;
- `adjacent` — запрос ведёт к продукту через одну понятную задачу;
- `exploratory` — гипотеза без подтверждённого предложения;
- `irrelevant` — вне продукта.

Обязательная тема может пройти ниже порога только со статусом `watch`; она не становится приоритетной без материального спроса.

## 5. Создать кластеры

Кластеризовать по сочетанию:

`core_entity + intent + customer_job + solution_scope + region_scope`

Объединять только фразы, для которых одна страница или одно продуктовое действие полностью удовлетворяет намерение пользователя.

Никогда автоматически не объединять:

- информационный и коммерческий интент;
- общий запрос и конкретный бренд/продукт, если ответы различаются;
- разные задачи клиента;
- разные регионы с отдельными предложениями;
- товарный спрос и спрос на обучение;
- внедрение готового решения и самостоятельную разработку.

Следовать `references/clustering-policy.md`. Для каждого кластера сохранять:

- стабильный `cluster_id`;
- каноническое название;
- репрезентативные запросы;
- все алиасы;
- интент, сущность, задачу и продукты;
- уровень близости;
- покрытие сайта;
- решение `include`, `watch`, `review` или `reject`;
- причины решения;
- историю merge/split/rename.

Не менять существующий `cluster_id` при смене канонической фразы. Merge или split выполнять только с записью в `change_log`.

## 6. Выбрать ряды для динамики

Для каждого `include`-кластера выбрать 1–5 репрезентативных запросов. Выбирать по порядку:

1. соответствие интенту и продукту;
2. достаточная частотность;
3. однозначность формулировки;
4. стабильная история;
5. отсутствие вложенного дубля.

Не суммировать вложенные фразы как независимый спрос. Для `watch` получать динамику только при обязательной теме, существующем товаре/URL или явном новом спросе.

Получить минимум 24 полных месяца, предпочтительно 36:

```text
methodCode: wordstat.dynamics.read
params: {"phrase":"...","period":"monthly","fromDate":"YYYY-MM-01","toDate":"YYYY-MM-DD","regions":[geo_id],"devices":["all"]}
```

Не включать текущий неполный месяц. Не сравнивать ряды с разными регионами или устройствами.

## 7. Рассчитать тренды

Подготовить `input.json` по `references/data-contract.md` и выполнить:

```bash
python3 scripts/analyze_trends.py input.json --history-db trend-history.sqlite --json trend-report.json --markdown trend-report.md
```

Классы: `breakout`, `emerging`, `rapid_growth`, `growing`, `seasonal_rise`, `seasonal_fall`, `structural_decline`, `declining`, `stable`, `watch`, `insufficient_data`.

Не выдавать сигнал только по проценту. Учитывать объём, историю ненулевого спроса, согласованность метрик, волатильность, близость к продукту и покрытие сайта. Отмечать пропуски, дубли, отрицательные значения, неполный месяц и выбранный метод сезонной декомпозиции. Прогнозировать только направлением: `вверх`, `вниз` или `неопределённо`.

## 8. Проверить бизнес-смысл

Перед рекомендацией проверить:

1. Кластер присутствует в подтверждённом реестре или прошёл формальный review.
2. Спрос соответствует аудитории и задаче клиента.
3. Всплеск не вызван новостью, омонимом, ботами или единичным событием.
4. Существующую страницу нельзя разумно усилить вместо создания новой.
5. Направление подтверждается связанными запросами и, если доступны, Вебмастером, Метрикой, CRM или продажами.

Для Вебмастера подготовить явное соответствие `query → cluster_id → URL`, затем объединить данные:

```bash
python3 scripts/merge_webmaster_visibility.py trend-report.json webmaster-export.json --json visibility-report.json
```

Не подменять Wordstat метриками видимости. Использовать только следующие выводы: `market_rising_no_page`, `optimize_visibility`, `improve_ctr`, `review_offer`.

Google Trends использовать только как дополнительную относительную проверку. Wordstat остаётся основной измерительной системой.

## 9. Назначить действие

- `gap` + информационный интент → статья, FAQ или тематический хаб.
- `gap` + коммерческий интент → проверить продуктовую экономику, затем посадочную.
- `partial` → обновить существующую страницу.
- `covered_product` без контента → поддерживающий контент и перелинковка.
- `declining` при существующем предложении → проверить замещающие формулировки, продажи, маржу и видимость.
- `review` → не создавать контент и продукт до подтверждения человеком.

Не предлагать удаление страницы или товара только по Wordstat. Не писать и не публиковать контент автоматически.

## 10. Выдать отчёт и аудит охвата

Начать с 3–7 сигналов, требующих решения. Для каждого показать кластер, метрики, покрытие, бизнес-связь, действие, уверенность и приоритет.

Обязательно добавить контроль качества исследования:

- число активных seed-фраз;
- число кандидатов Wordstat;
- долю `include`, `watch`, `review`, `reject`;
- причины отклонения;
- обязательные темы без спроса;
- кандидаты без назначенного кластера;
- новые, объединённые и разделённые кластеры;
- долю товаров, услуг, аудиторий и задач, покрытых seed-фразами.

Если необработанных кандидатов больше порога из реестра, не называть исследование полным.

## 11. Регулярный мониторинг

На каждом цикле:

1. Использовать прежний подтверждённый реестр и cluster IDs.
2. Обновить последний полный месяц.
3. Повторно собрать top requests для discovery.
4. Новые фразы записать в ledger; не включать автоматически при `exploratory`.
5. Пересчитать сигналы.
6. Показать только новые сигналы, смену статуса и существенное ускорение/замедление: `new_growth`, `new_decline`, `accelerating`, `decelerating`, `recovered`, `lost_materiality`, `new_demand`.
7. Сохранить решения пользователя, чтобы не возвращать отклонённые темы без новых оснований.

Skill выполняет анализ, но не запускается по времени. Автоматизацию создавать отдельно после согласования расписания.

## Ограничения

- Говорить «сигнал» или «оценка направления», а не «точный прогноз».
- Не считать черновой реестр подтверждённым.
- Не скрывать отклонённые запросы и причины.
- Не переносить выводы одного региона на другой.
- Не делать вывод о падении по одному месяцу.
- Не считать нулевые месяцы до появления запроса историей сезонности.
- Не путать рыночный спрос Wordstat с видимостью сайта.

## Переносимость и запуск

Пути к ресурсам ниже относительны корню установленного навыка. Перед запуском
определи этот корень через механизм платформы; не предполагай текущую папку.
Относительные примеры CLI разрешай в абсолютный путь к скрипту, сохраняя рабочую
папку результата отдельно. Переменные и механизмы конкретной платформы задаются
её адаптером, не являются зависимостью универсальной методологии. Без Python, сети или коннектора запросить нормализованный вход или
вернуть ограниченный результат с явным статусом «не проверено».

Здесь capability обозначает возможность, а не гарантированное имя MCP-команды.
Вызовы в примерах — схема: сначала прочитать объявленные инструменты и сопоставить
аргументы. Не устанавливать зависимости, не создавать расписания, не публиковать
и не отправлять сообщения без применимого разрешения пользователя.
