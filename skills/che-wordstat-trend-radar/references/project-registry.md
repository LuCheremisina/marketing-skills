# Обязательный реестр проекта

## Назначение

`project-registry.json` фиксирует границы исследования. Без валидного реестра разрешать только разведочный сбор без стратегических выводов.

Использовать шаблон `assets/project-registry.template.json`.

## Обязательные разделы

| Раздел | Что фиксировать |
|---|---|
| `project` | ID, название, домен, регионы, устройства, статус реестра |
| `products_services` | Реальные товары и услуги, статус, приоритет, URL и seed-фразы |
| `product_categories` | Иерархию направлений и связь с продуктами |
| `audiences` | Сегменты, проблемы и связь с задачами |
| `customer_jobs` | Формулировки задач, этап пути, продукты и seed-фразы |
| `existing_urls` | URL, тип страницы, тема, интент и продукты |
| `themes.required` | Темы, которые нужно отслеживать даже при малом спросе |
| `themes.forbidden` | Омонимы, нежелательные и нерелевантные темы |
| `relevance_policy` | Числовые уровни близости и минимальный допуск |
| `thresholds` | Частотность, лимиты кандидатов и допустимый остаток review |
| `clustering_rules` | Поля объединения, обязательные разделения и стабильные ID |

## Статусы

- `draft` — AI или пользователь предложил запись, но она ещё не влияет на основной анализ.
- `active` — запись подтверждена и участвует в seed-manifest.
- `paused` — временно исключена, история сохраняется.
- `retired` — продукт или тема закрыты; использовать для сигналов падения только при сохранённой бизнес-экспозиции.

Весь реестр проекта переводить в `confirmed` только после заполнения обязательных разделов. Отдельные элементы всё равно могут оставаться `draft`.

## Источники реестра

Использовать по приоритету:

1. Подтверждённые вводные пользователя.
2. Каталог товаров и услуг.
3. Структуру сайта, sitemap и меню.
4. CRM или продуктовый справочник без персональных данных.
5. Существующую семантику и Вебмастер.
6. Гипотезы AI — только `draft`.

Не считать наличие статьи доказательством наличия услуги. Не превращать популярную тему в продукт без подтверждения.

## Изменения

При изменении реестра записывать в `change_log`:

- дату;
- автора решения: `user`, `source`, `ai_proposal`;
- тип: `add`, `update`, `pause`, `retire`, `merge`, `split`;
- объект и ID;
- причину;
- старое и новое значение, если применимо.

Не перезаписывать историю решений.
